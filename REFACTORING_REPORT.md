# Рішення щодо рефакторингу

## Модулі

- `app.js` — створення Express-застосунку, JSON middleware, `/health`, підключення маршрутизатора, 404 для невідомого маршруту та централізована обробка помилок.
- `src/routes/orders.js` — HTTP-рівень Orders API: маршрути, статус-коди, заголовок `Location` і JSON-формат помилок.
- `src/services/orders-service.js` — бізнес-правила: валідація, нормалізація полів, серверний розрахунок `total`, формування публічного представлення замовлення.
- `src/store/order-store.js` — зберігання в пам'яті та операції додавання, пошуку, списку й видалення. Сховище не залежить від Express.

## Очищення коду

- Видалено `slopify`: функція лише друкувала незрозуміле повідомлення в консоль і викликала `next()`. Вона не змінювала `req`, `res`, заголовки, тіло відповіді чи маршрут. Автоматичні тести не вказують на залежність від її побічного ефекту.
- Видалено штучне очікування `synchronizeOrderState()` (випадкова затримка 900–2000 мс) і допоміжні `prepareOrderContext()`, `persistOrderWithContext()` та `verifyOrderStateForRemoval()`. Контекст лише повертав запис і кількість елементів, а перевірка порівнювала довжину масиву з його щойно прочитаною довжиною. Це додавало затримку без корисної перевірки.
- Видалено невикористаний `LEGACY_REGION` і функцію `unusedLegacyOrderCode()`.
- Не зберігається внутрішнє поле `createdAt`, оскільки жоден маршрут чи бізнес-операція його не використовували, а публічна відповідь його не містила.
- Оновлено `AGENTS.md`: замість необґрунтованої вимоги зберігати `slopify` записано правило перевіряти фактичні ефекти legacy-коду.

## API-контракт

Публічні маршрути не змінено: `POST /orders`, `GET /orders`, `GET /orders/:id`, `DELETE /orders/:id`, `GET /health`. Збережено формати відповідей, серверне обчислення `total`, статус `created`, валідацію, `Location` для успішного створення, коди 201/200/204/400/404 і структуровані помилки. Додані тести для сервісних правил, некоректного JSON, видалення невідомого замовлення та невідомого маршруту.

## Швидкодія

Повторні числові вимірювання в цьому середовищі не вдалося отримати: `npm ci` не завершився, бо середовище не змогло розв'язати `registry.npmjs.org`, а `express` відсутній. Тому результати «до» та «після» не вигадуються. Після встановлення залежностей виконайте команди нижче й скопіюйте отримані цифри в таблицю.

| Метрика | До | Після |
|---|---:|---:|
| Середня затримка | не виміряно | не виміряно |
| p50 | не виміряно | не виміряно |
| p95 | не виміряно | не виміряно |
| p99 | не виміряно | не виміряно |
| Пропускна здатність | не виміряно | не виміряно |

За початковим кодом найповільнішими мали бути успішні `POST /orders` та `GET /orders/:id`, а також `DELETE /orders/:id`: кожен шлях очікував випадкові 900–2000 мс. `GET /health`, `GET /orders` і відповіді 404 такого очікування не мали. Після рефакторингу цей штучний шлях затримки видалено; фактичні цифри потрібно підтвердити повторним `npm run load`.

Команди для перевірки (у двох терміналах):

```sh
npm install
npm test
npm start
# у другому терміналі
npm run load
```

## Перевірка AI-змін

AI запропонував видалити `slopify` попри напис «CRITICAL» та твердження в `AGENTS.md`, що middleware обов'язковий. Зміна перевірена читанням функції: вона лише робила `console.log(...)` і `next()`, не змінюючи запит або відповідь. Її видалення прибирає шум у логах і не змінює API-контракт. Через відсутність мережевого доступу до npm у цьому середовищі повний інтеграційний прогін не підтверджено тут; перед здачею необхідно запустити команди перевірки у середовищі, де доступний npm registry.
